# Размещение Kromka

## Действующее MVP: tokenapp.ru, 21 ноября 2026

На VPS `185.84.162.91` развёрнут снимок локальной версии 0.2.0, включая ещё не закоммиченную подготовку к релизу. Адрес: `https://tokenapp.ru`. Старый прокси Focus с этого сервера снят. Сайт `vozdvizhen.ru` продолжает работать отдельно.

- Node 24.22.3: `/opt/kromka-node/bin/node`, приложение: `/opt/kromka/current` → `/opt/kromka/releases/initial-20261121`.
- Служба: `kromka.service`, Node слушает только `127.0.0.1:4188`, Python sidecar — `127.0.0.1:8765`.
- Конфигурация и ключи: `/etc/kromka/app.env`, права 0600. Секреты не находятся в репозитории или web-root.
- Постоянный кеш: `/var/lib/kromka/cache`, сохраняется между обновлениями кода.
- Nginx: `/etc/nginx/conf.d/kromka.conf`; HTTPS и автоматическое продление существующего сертификата `tokenapp.ru` восстановлены. Access log приложения выключен; error log: `/var/log/nginx/kromka-error.log`.
- Ежедневный backup: `kromka-backup.timer`, архивы настроек и кеша `/var/backups/kromka`. Удаляются только архивы этого таймера старше семи суток. Это локальная копия, а не защита от потери VPS.
- Проверки: `systemctl status kromka`, `journalctl -u kromka -n 50`, `curl -fsS https://tokenapp.ru/healthz`. Спортивные данные отдельно: `/api/rpl`. Первый холодный запрос Flashscore может не уложиться в тайм-аут Node, при этом резерв GOAL API работает; после прогрева proxy возвращает 240 матчей.

Деплой выполнен загрузкой снимка. Автоматического обновления из GitHub нет: локальная версия содержит незакоммиченные изменения и отличается от `main`. Для следующего релиза сначала проверить и сохранить полный набор изменений, загрузить отдельный каталог `releases`, проверить тесты и переключить `current`; `/etc/kromka` и `/var/lib/kromka` сохранять. Перезапуск: `systemctl restart kromka`. Не включать слепой `git pull` поверх этой установки.

### Push: ещё не реализован

Файл `/etc/kromka/push.env` зарезервирован для `RUSTORE_PROJECT_ID`, `RUSTORE_SERVICE_TOKEN`, `KROMKA_PUSH_ENABLED=false`; текущий веб-сервер его не использует. Проверка готовности без отправки сообщений:

```bash
/opt/kromka-node/bin/node --env-file=/etc/kromka/push.env /usr/local/lib/kromka/push-check.mjs
```

Пока отсутствуют проект RuStore, Android SDK, регистрация токенов и подписок на сервере, постоянный обработчик новых событий, дедупликация и очередь доставки. Одно размещение веб-сервера их не создаёт. Следующий этап — реализовать эти компоненты, обновить политику под хранение push-токенов и проверить реальную доставку на телефоне. Сервисный токен вводить только в закрытый файл на VPS. Официальный API: `https://www.rustore.ru/help/sdk/push-notifications/send-push-notifications`.

Документы приложения остаются редакцией к выпуску: название провайдера, фактический дата-центр и срок хранения технических журналов нужно подтвердить в панели хостинга и заполнить в `app.env`. Домен уже установлен как `APP_PUBLIC_URL=https://tokenapp.ru`.

Приложение разворачивается одним Docker web service: Node 24 обслуживает PWA/API и запускает Python-прокси только на `127.0.0.1:8765`. Снаружи открыт только Node на `$PORT`.

## Публичный релиз в России

Планируется российский хостинг серверной части и Android APK в RuStore. Российский провайдер, дата-центр и домен ещё не выбраны; существующий Render ниже — прежнее тестовое окружение, не подтверждение размещения в России. Автоматического переноса инфраструктуры в этой подготовке нет.

После настройки реального окружения заполните `APP_PUBLIC_URL` (HTTPS без пути), `LEGAL_HOSTING_PROVIDER`, `LEGAL_HOSTING_COUNTRY=RU`, `LEGAL_HOSTING_LOCATION`, `LEGAL_LOG_RETENTION_DAYS` в переменных сервера. Срок журналов должен совпадать с условиями и настройками провайдера. Эти переменные публикуют сведения в документах, а не меняют размещение или хранение данных.

Проверьте `npm run check`, `npm test` и `npm run release:check` с переменными окружения. Для проверки самого процесса есть `/healthz` без обращения к спортивным источникам. Публичные `/privacy`, `/terms`, `/storage`, `/support`, `/licenses`, `/about` должны обслуживаться Node-сервером; статический хостинг одного `index.html` их не заменяет. Sitemap использует только подтверждённый `APP_PUBLIC_URL`; до заполнения конфигурации индексация закрыта.

Сборка Android и загрузка в RuStore — отдельный этап: [RUSTORE-RELEASE.md](RUSTORE-RELEASE.md). Итоговые SDK и разрешения APK нужно сверить с политикой перед отправкой. Полный порядок: [RELEASE-CHECKLIST.md](RELEASE-CHECKLIST.md), работа с обращениями и данными: [RELEASE-OPERATIONS.md](RELEASE-OPERATIONS.md).

## Render Free

В Render создайте Web Service из публичного репозитория `https://github.com/DmitryStuzhin/kromka`, ветка `main`. Выберите Docker, регион Frankfurt, **Free** и Dockerfile `./Dockerfile`. Health check: `/api/status`. Blueprint `render.yaml` содержит те же настройки для воспроизводимого запуска.

Задайте `GOAL_API_KEY` и `API_FOOTBALL_API_KEY` только в серверных Environment Variables Render. Не вставляйте значения в Dockerfile, YAML, GitHub, клиентский код или логи. Ключ GOAL нужен для дополнений и полного резерва; API-Football используется только для недостающих портретов.

Render выдаёт постоянный HTTPS-адрес `*.onrender.com`. Это не временная ссылка среды разработки. Адрес действует, пока существует сервис и соблюдены условия провайдера; бесплатный тариф не гарантирует uptime.

## Обновления

При подключении через Public Git Repository автоматическое развёртывание обычного сервиса недоступно: после изменения `main` выберите **Manual Deploy → Deploy latest commit**. Для автоматизации можно позднее подключить Blueprint либо GitHub integration с доступом только к этому репозиторию. `render.yaml` использует `autoDeployTrigger: checksPass`.

## Ограничения без оплаты

- После 15 минут без входящего трафика сервис засыпает. Первое открытие после простоя может занять около минуты. Не используйте искусственные keep-alive запросы.
- Render Free имеет временную файловую систему: `.cache` и локальный дневной счётчик API-Football теряются при остановке/перезапуске/деплое. Лимит 80 запросов в сутки действует только между такими сбросами; реальный провайдерский лимит остаётся отдельным ограничением. Для надёжной сохранности понадобится отдельное постоянное хранилище.
- В бесплатном workspace 750 instance-hours в месяц делятся между сервисами. Есть отдельные лимиты bandwidth/build. Без добавления платёжного метода превышение приводит к ограничению/приостановке сервиса, а не к покупке дополнительных ресурсов. Не добавляйте платёжный метод и не переходите на платный plan без согласования.
- Render может ограничить сервис при большом исходящем трафике. Нет гарантий производительности и доступности live-данных после сна.
- Публичные API-маршруты не требуют авторизации. Кэширование снижает расход запросов, но это не полноценная защита от злоупотреблений. Для масштабного запуска нужны общий лимитер и мониторинг квот.
- Неофициальный Flashscore feed и изображения не имеют подтверждённого разрешения на публичное/коммерческое повторное использование; детали в `DATA-SOURCE.md` и `MEDIA-SOURCES.md`.

Проверка: `npm run check && npm test`; после деплоя откройте `/`, `/manifest.json`, `/api/status` и `/api/rpl`. Не считайте `configured: true` подтверждением доступности провайдера: реальные fixtures/table проверяются отдельно.

Документация провайдера: https://render.com/docs/free и https://render.com/docs/blueprint-spec.
